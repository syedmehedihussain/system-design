Use Case Diagram

Source: CT2 Q1 · 10 marks · Lecture 7

Case study — Rent-A-Tool
Rent-A-Tool is a digital ecosystem connecting homeowners (Customers) with local professional Tool Owners. The system operates under the following specifications:

Account Management: Every user must have an Account featuring an accountID, balance, and minBalance. Accounts are specialized into ActiveAccount (permitting browsing and rentals) and SuspendedAccount (activated if the balance falls below minBalance). A suspended account only allows a payBalance() operation to return to Active status.

Inventory Structure: Tools are categorized as Power Tools, Hand Tools, or Heavy Machinery. All tools have a toolID and dailyRate. Heavy Machinery is a unique subclass requiring an additional “Insurance Verification” step before a rental is finalized.

Rental Workflow: A Customer initiates a rental by selecting a tool from the Inventory Database. The System first verifies the account status. If the account is Active and the tool is available, the system calculates the rentalFee.

Transaction & Security: The System requests payment from a Payment Gateway. If the gateway confirms the transaction, a Rental Order is created, linking the Customer to the specific Tool. If the payment fails, the system shows an error and cancels the order. For Heavy Machinery, the system concurrently verifies insurance with a third-party provider before the owner confirms tool pickup.

Completion: Upon tool return, the Owner updates the status. If the customer has completed more than five rentals, a Discount Coupon is automatically generated and linked to their account for future use.
Identify all primary and supporting actors and depict a Use Case Diagram for the platform with all core use cases. 10 Marks

Step 1 — Understand what is being asked

Two deliverables in one question: (a) a written list of actors split into primary and supporting, and (b) the diagram. If you only draw the diagram you lose the actor-identification marks. Write the list above the diagram.

Step 2 — Sort your circled actors

  • Primary actor = starts an interaction to get a goal for themselves. Ask "does this person want something from the system?" → Customer (wants to rent), Tool Owner (wants to list tools and confirm pickup).
  • Supporting actor = the system reaches out to it to finish the job; it never starts anything. → Payment Gateway, Insurance Provider.
  • Not an actor: "Inventory Database" — it is a data store inside the system. Do not draw it as a stick figure.

Step 3 — Turn your boxed verbs into use case names

Each must be verb + noun, describing what not how. Group them by which actor cares:

  • Customer: Create/Manage Account, Pay Balance, Browse/Search Tools, Rent Tool
  • Inside the rental (always happens → <<include>>): Verify Account Status, Check Tool Availability, Calculate Rental Fee, Process Payment, Create Rental Order
  • Conditional (→ <<extend>>, from your ★ marks): Verify Insurance [only Heavy Machinery], Generate Discount Coupon [only if rentals > 5]
  • Tool Owner: List/Manage Tool, Confirm Tool Pickup, Update Return Status

Step 4 — Draw in this order

  1. Big rectangle, write “Rent-A-Tool System” across its top edge.
  2. Stick figures: primary actors down the left, supporting actors down the right. Label each "(primary)" / "(supporting)".
  3. Ovals inside, grouped so related ones sit near each other.
  4. Plain lines from actor to the use cases they take part in.
  5. Dashed stereotyped arrows last: <<include>> points from Rent Tool to the sub-behaviour; <<extend>> points from the conditional behaviour to the base use case, with the condition written next to it.

Answer

Primary actors: Customer (Homeowner), Tool Owner · Supporting actors: Payment Gateway, Insurance Provider. Write this list above the diagram — the question asks for it separately.
Marker's checklist
  • Actor list written out and split primary / supporting ✔
  • Named system boundary box ✔
  • 8–11 use cases, all verb + noun ✔
  • At least one <<include>> and both <<extend>> conditions shown with the guard text ✔
  • Payment Gateway and Insurance Provider connected to the correct use cases, not to the actor ✔
  • Inventory Database NOT drawn as an actor ✔

Use Case Narration

Source: Final Aut24 Q2c · 10 marks · Lecture 7

Case study — forwarding NOC or rejection letter
The paper gives a process diagram of this process. In words: the Officer identifies the pending cases from the case data. Each case is either rejected — in which case a rejection letter is forwarded to the Proponent — or approved — in which case the NOC is forwarded to the Proponent. Either way the case data is then updated and stored in the CASE DB.
Prepare a use case narration for the above process. 10 Marks (left blank in the answer key)

How to build it in 5 minutes

  1. Copy the three-section skeleton from Lecture 7 slide (Figure 10.7): identification & initiation · steps performed · conditions, assumptions, questions.
  2. Fill identification from the DFD you just drew: the primary actor is whoever the first data flow comes from (Officer); the other actors are the remaining entities (Proponent) plus the System.
  3. Fill the steps from the sequence diagram you just drew — every message becomes one numbered row, actor messages on the left, system responses on the right.
  4. Write pre/postconditions by asking “what must be true before?” and “what is true after?”.
  5. Add one alternate course — there's always one hiding in the case study.

StakeholdersProponent, Officer, the approving authority

Construct an Activity Diagram for the “Process Rental Payment” use case. 10 Marks

Step 1 — Understand the scope

The question names one use case. Do not model account creation or tool return. Your diagram starts when the customer triggers a rental and ends when the order is created (or cancelled). The relevant paragraphs are “Rental Workflow” and “Transaction & Security”, plus the coupon sentence in “Completion”.

Step 2 — Decide the swimlanes

Ask "who performs each action?" Three answers appear in those paragraphs: the Customer (selects), the System (verifies, calculates, creates, cancels), the Payment Gateway (confirms). So: 3 swimlanes. Put the initiator leftmost.

Step 3 — Convert each ★ into a decision diamond

Sentence in the caseBecomes
“The System first verifies the account status”Activity [Verify account status] then ◆ with guards [Active] / [Suspended]
“If the account is Active and the tool is available”A second ◆ with [available] / [not available]
“If the gateway confirms … If the payment fails”◆ with [payment confirmed] / [payment failed]
“If the customer has completed more than five rentals”◆ with [rentals > 5] / [rentals ≤ 5]

Step 4 — Draw in this order

  1. Three labelled columns with vertical dividing lines.
  2. Filled circle ● at the top of the Customer lane.
  3. Work down: one rounded rectangle per action, in the lane of whoever does it. When the doer changes, the arrow crosses the divider.
  4. Every diamond gets both branches labelled in square brackets — an unlabelled branch loses marks.
  5. Each failure branch gets its own bullseye ◉ end node. Don't leave an arrow hanging.

Answer

Three swimlanes, four decision diamonds with guards, a separate end node for every failure path.
Marker's checklist
  • 3 swimlanes with headers ✔ · start node ● ✔ · every path ends in ◉ ✔
  • 4 decision diamonds, both branches guarded in [ ] ✔
  • Activities are verb phrases in rounded rectangles, never questions ✔
  • The cancel-order path from payment failure is shown (explicit in the case) ✔
  • Coupon generation appears as a conditional branch ✔

Create a Sequence Diagram representing a successful rental of a Heavy Machinery item. 15 Marks

Step 1 — Notice the two constraints in the question

  • “successful” → draw only the happy path. No error branches, no cancel-order. Drawing failures wastes time and clutters the diagram.
  • “Heavy Machinery” → you must include the insurance verification step and the owner's pickup confirmation, and they happen concurrently per the case study.

Step 2 — Choose and order the participants (three-layer rule from Lecture 7)

  1. Actor — Customer (comes from the use case diagram; the lecture says always include it)
  2. Interface / boundary class — :RentalUI (the screen the customer uses)
  3. Control class — :RentalController (orchestrates the steps)
  4. Entity classes — :Account, :HeavyMachinery, :RentalOrder
  5. External systems — :PaymentGateway, :InsuranceProvider, and the ToolOwner actor at the far right

Step 3 — Turn the case's sentences into messages, in order

#Case sentenceMessage
1“A Customer initiates a rental by selecting a tool”selectTool(toolID) → UI → requestRental() → Controller
2“The System first verifies the account status”verifyStatus(custID) → :Account, returns ACTIVE
3“and the tool is available”checkAvailability(toolID) → :HeavyMachinery, returns true
4“the system calculates the rentalFee”calculateFee() — a self-call on the controller
5“requests payment from a Payment Gateway … confirms”requestPayment(fee) → :PaymentGateway, returns paymentConfirmed
6“concurrently verifies insurance … before the owner confirms pickup”verifyInsurance() → :InsuranceProvider and requestPickupConfirmation() → ToolOwner
7“a Rental Order is created, linking the Customer to the specific Tool”create() → new :RentalOrder object

Step 4 — Draw in this order

  1. Boxes across the top, left to right in the order above. Names as :ClassName.
  2. Dashed lifelines all the way down the page.
  3. Add messages one at a time, each strictly lower than the last — time only flows down.
  4. Draw a thin activation bar on the receiver while it is busy.
  5. Add the dashed return arrow for every request, labelled with the value returned. These carry marks.
  6. For the concurrent pair, bracket them and write “concurrent” beside them (or draw a par frame).
  7. Draw the :RentalOrder box lower down at the point it is created, with the create() arrow pointing into it.

Answer

Interface → control → entity layering; every request has a dashed labelled return; RentalOrder is created part-way down.
Marker's checklist
  • Actor from the use case diagram is present ✔
  • Interface → control → entity layering visible ✔
  • Every request has a labelled dashed return ✔
  • Insurance verification present (it's the whole point of choosing Heavy Machinery) and shown as concurrent ✔
  • RentalOrder shown being created, not sitting at the top ✔
  • No failure branches — the question said successful ✔

Statechart Diagram

Not asked in CT2, CT3, Sum25 or Aut24 · method drill · Lecture 7

Drill question (constructed from the Rent-A-Tool case, not from a past paper). Draw a statechart diagram for the Account class. Method drill

Step 1 — Pick one class with a life cycle

A statechart is drawn for a single class, never for the whole system. Choose one whose object visibly changes condition over time: Account, RentalOrder, Job, Student. The CT2 case hands you Account directly, since it is specialized into ActiveAccount and SuspendedAccount.

Step 2 — List the states, not the actions

States are conditions of being, so they read as adjectives or past participles: Active, Suspended, Closed. If you catch yourself writing a verb inside a state box you are drawing an activity diagram by mistake.

Step 3 — Label every transition with the event that causes it

Transitions are the verbs and the triggers, optionally with a guard in brackets: [balance < minBalance], payBalance() [balance ≥ minBalance]. An unlabelled arrow earns nothing.

Step 4 — Start and finish properly

A filled circle marks the initial state, and a bullseye marks the final state if the object's life actually ends. Not every statechart needs a final state, but Account does once it can be closed.

Answer

Account has exactly the two states the case study names, plus a terminal Closed state. The return transition carries both the event and the guard, which is where the marks concentrate.

Same method, different class: RentalOrder runs Created → Paid → Active → Returned → Closed, with the payment failure branch going straight from Created to Cancelled.

Marker's checklist
  • One class named as the diagram title ✔
  • Initial filled circle present ✔
  • States are conditions of being, transitions are events ✔
  • Every transition labelled, guards in square brackets ✔
  • Final state shown as a bullseye ✔

Deployment Diagram

Source: Final Aut24 Q4 · 10 marks · Lecture 7

IRAS currently has the following deployment diagram (App Server running IIS and Oracle i · Client Device running Chrome, connected over the Internet with JavaScript · Database Server running Oracle, connected over LAN with DB). We need to integrate SSC HSC result validation from the result portal with external APIs. Reflect the change in the existing deployment diagram. 10 Marks

Step 1 — Understand what “reflect the change” means

You must redraw the entire existing diagram and then add the new part. Drawing only the new node scores badly — part of the marks is reproducing the given nodes, their software, and their labelled connections correctly.

Step 2 — Decide where the new node attaches

Ask: which machine actually calls the API? The App Server runs the business logic, so it makes the outbound API call. Not the client device (browsers don't hold API credentials) and not the database server (it's behind the LAN). Connect the new node to the App Server.

Step 3 — Label the new communication path

Every connection in a deployment diagram carries a protocol/network label. The existing ones say “Internet”, “javaScript”, “LAN”, “DB”. Yours should say HTTPS / REST API over Internet.

Answer

Every original node redrawn with its software and labels, plus one new external node attached to the App Server over HTTPS / REST API.
Marker's checklist
  • All three original nodes redrawn, with their software inside ✔
  • Original labels kept: Internet, javaScript, LAN, DB ✔
  • One new external node, clearly marked as external ✔
  • Connected to the App Server, with an HTTPS / REST API label ✔

Draw DFD diagrams (Level 0, 1, 2). 10 + 15 + 10 Marks

Step 1 — Level 0 (Context Diagram): rules from Lecture 8

  1. Exactly one process, numbered 0, named after the whole system.
  2. All external entities drawn around it as double squares.
  3. Only the major data flows in and out — don't draw all 14 flows, group them (“service request, rate offer, payment authorization, rating”).
  4. No data stores. This is the rule people break most often — the Job Records db does NOT appear here.
  5. No other processes.

Answer — Level 0 / Context Diagram

Level 0: one process numbered 0, all four entities, NO data stores.

Step 2 — Level 1 (Diagram 0): rules

  1. Explode process 0 into the seven processes, numbered 1–7 in event-table order.
  2. Every entity and every flow from the context diagram must reappear — this is balancing, and it is marked. Nothing new may cross the boundary.
  3. Now add the data stores and connect them to the processes whose Activity column mentioned them.
  4. Arrow into a store = writing; arrow out of a store = reading. Row 1 does both (“track quantity … in Job Records db” = write; “fetch average rates” = read).
  5. Never connect a data store straight to an entity.

Answer — Level 1 / Diagram 0

Level 1: one process per event-table row (7 rows → 7 processes), six data stores, boundary flows identical to Level 0.

Step 3 — Level 2 (child diagram): which process to explode and how

  1. Pick the process with the most verbs in its Activity cell. Row 4 says: calculate the final fee incorporating the accepted hourly rate, actual duration, and detailed charge breakdowns for material costs, traveling charges and other expenses; generate invoice. That's four distinct steps — perfect for exploding. (Process 3 is the second-best candidate.)
  2. Number the children after the parent: 4 → 4.1, 4.2, 4.3, 4.4. Never restart at 1.
  3. Balance it: the parent's only input was “job Finished”, its only output was “final invoice”. So exactly one flow enters the child diagram and exactly one leaves it. Anything else is an internal flow between children, or a flow to a data store.
  4. Don't draw external entities on a child diagram (Lecture 8 rule). Show the incoming/outgoing flows at the edge instead.

Answer — Level 2, child diagram of process 4

Level 2: process 4 exploded into 4.1–4.4, balanced with its parent (one flow in, one flow out).
Marker's checklist for all three levels
  • Level 0 has one process numbered 0 and zero data stores ✔
  • Level 1 has ≤ 9 processes, numbered 1–7, matching the event table rows ✔
  • Same entities and same boundary flows on Level 0 and Level 1 (balanced) ✔
  • All six data stores present and labelled D1–D6 ✔
  • No data store touching an entity directly; no entity touching an entity ✔
  • Every process has ≥ 1 input and ≥ 1 output ✔
  • Level 2 children numbered 4.1–4.4 and balanced with the parent ✔
  • All flows labelled with nouns, all processes with verb phrases ✔

  • 6 → D6 = U — “update average rating for the user's profile”.
  • 7 → D2 = R/U — reads rates to analyse, then “adjust pricing parameters” writes back.

Summary lines to finish with: Clients mainly Create requests and Read invoices/receipts · Contractors Create acceptances and Update job status · Service Rate History is touched by every pricing-related process · Payment Transactions is created only at process 5 · the System reads across all stores to generate the Admin's demand report.

Process Spec — Decision Table & Tree

Not asked in CT2, CT3, Sum25 or Aut24 · method drill · Lecture 9

Drill question (constructed from the Rent-A-Tool case, not from a past paper). A rental is approved only when the account is Active, the tool is available, and the gateway confirms payment. Build the decision table, simplify it, then redraw the same logic as a decision tree. Method drill

Step 1 — Draw the four quadrants

Top-left holds the conditions, top-right the condition alternatives, bottom-left the actions, bottom-right the action entries. Nothing else goes in a decision table.

Step 2 — Count the columns before you draw them

Columns = alternatives raised to the number of conditions. Three yes/no conditions give 2³ = 8 rule columns. Draw all eight even if some collapse later, otherwise you cannot prove completeness.

Step 3 — Fill the alternatives by halving

First condition: fill the first half Y, the second half N. Second condition: halve again (YYNN YYNN). Third: alternate every column (YNYN YNYN). This mechanical pattern is what guarantees no combination is missed.

Step 4 — Put an X where the rule triggers the action

Work down one column at a time and ask what the business actually does under that exact combination. Blank cells are correct answers.

Answer — full table, all 8 rules

Conditions12345678
C1 · Account is ActiveYYYYNNNN
C2 · Tool is availableYYNNYYNN
C3 · Payment confirmedYNYNYNYN
Actions
A1 · Calculate fee and request paymentXX
A2 · Create Rental OrderX
A3 · Display error and cancel orderXXXXXXX
A4 · Prompt payBalance() to reactivateXXXX

Simplified table

Rules 3 and 4 have identical actions and differ only in C3, so C3 stops mattering and becomes a dash. Rules 5 to 8 are all identical, so both C2 and C3 collapse. Four rules survive:

ConditionsR1R2R3R4
C1 · Account is ActiveYYYN
C2 · Tool is availableYYN–
C3 · Payment confirmedYN––
Actions
A1 · Calculate fee and request paymentXX

A3 · Display error and cancel orderXXX
A4 · Prompt payBalance() to reactivateX

Answer — the same logic as a decision tree

One condition per node, branching left to right in the order the business actually checks them, an action at every leaf. Four leaves for four surviving rules, which is the cross-check that the tree and the table agree.

Structured English for the same logic

IF account status is Active
    IF tool is available
        calculate rentalFee
        request payment from Payment Gateway
        IF payment confirmed
            create Rental Order
        ELSE
            display error
            cancel order
    ELSE
        display error
        cancel order
ELSE
    prompt payBalance() to reactivate account
    cancel order

  • Four quadrants drawn and labelled ✔
  • Column count justified as 2³ = 8 ✔
  • Alternatives filled by the halving pattern, no combination missing ✔
  • Simplification shown with dashes, and the merge explained ✔
  • Checked for the four problems: incompleteness, impossible situations, contradictions, redundancy ✔
  • Tree leaves match the simplified rule count ✔

Output Report & Chart

Source: Final Aut24 Q1b · 10 marks · Lecture 10

Prepare an output chart/graph/image for the following data table (10 countries: Total Cases, Total Deaths, Recovered — USA 111.8M cases / 1.22M deaths … Russia 24.1M / 402K). 10 Marks

Step 1 — Read the marking scheme hidden in the answer key

“Chart with all the data point. For Data display 6 marks. 1 mark for axis labels, title and series.” So: 6 + 1 + 1 + 1 + (1 for neatness). Which means plot every one of the 10 countries — not a sample — and never forget the title, axis labels and legend.

Step 2 — Choose the chart type from the data shape

Ten discrete categories (countries) being compared → column/bar chart. Not a line chart (there's no time axis), not a pie (three different measures).

Step 3 — Handle the scale problem

Total Cases are ~100 million; Total Deaths are ~1 million — a hundred times smaller. On one axis the death bars would be invisible. Use a secondary y-axis on the right for deaths and say so in the legend. This is also the output bias point from Lecture 10 — an unbalanced scale misleads the user.

Answer

All ten countries plotted, title, both axis labels, legend, and deaths on a secondary axis so they stay visible.
Marker's checklist
  • All 10 countries plotted ✔ (6 marks)
  • Chart title ✔ · both axis labels with units ✔ · legend naming all three series ✔
  • Deaths on a secondary axis so they are visible ✔
  • N/A values shown as blank, not as zero (avoids bias) ✔

Input Form

Source: Final Aut24 Q1a · 10 marks · Lecture 11

Prepare an input form with required effective controls that will make the data collection and update smoother for the users to record the order and products under the order. 10 Marks
Field nameTypeComment
OrderIDChar(7)Id of the Order
OrdDateDateDate of the order
ItemIDChar(7)ID of the Items
itemNamevarchar(100)Name of the item
PriceIntPrice of the item
QuantityIntTotal Quantity of the item

Step 1 — Spot the one-to-many structure in the field list

“record the order and products under the order” — OrderID and OrdDate belong to one order; ItemID, itemName, Price, Quantity repeat for each product. So the form must have two zones: master fields at the top, a repeating data grid below. Putting all six fields in a flat column is the classic mistake here.

Step 2 — Map each type to a control

  • Char(7) OrderID → small text box, sized for 7 characters, read-only if auto-generated
  • Date OrdDate → calendar / date picker control (HTML5 date control from Lecture 11)
  • Char(7) ItemID → text box inside the grid, or a drop-down list if items come from a catalogue
  • varchar(100) itemName → wide text box (auto-filled once ItemID is chosen)
  • Int Price → numeric text box
  • Int Quantity → spin button (numeric, incrementable)

Step 3 — Add every scored “feature” (1 mark each)

The answer key says: “Input form with all the Attributes and controls like ADD, EDIT, SAVE, CLOSE, NAVIGATION. For each feature 1 mark.” So write them all in, plus a Delete button and a computed Total to show polish.

Answer

Master fields on top, repeating items in a data grid, and every scored feature: ADD, EDIT, SAVE, DELETE, CLOSE and navigation.
